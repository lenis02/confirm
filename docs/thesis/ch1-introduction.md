# 1. 서론

본 장에서는 프로젝트의 계획 수립과 회의 운영에서 나타나는 문제를 바탕으로 연구의 배경을 설명하고, 연구의 목적과 범위, 연구 방법, 논문의 구성을 차례로 제시한다.

## 가. 연구 배경

프로젝트 관리자(Project Manager, PM)는 프로젝트의 목표와 범위를 정하고, 이를 수행할 작업과 일정을 계획하며, 진행 과정에서 팀 사이의 의사소통과 의사결정을 조율한다. 이 가운데 계획 수립의 출발점이 되는 것이 작업 분할 구조(Work Breakdown Structure, WBS)이다. WBS는 프로젝트의 산출물과 작업을 관리 가능한 단위로 나눈 계층 구조로, 일정 수립, 인력 배정, 진척 관리의 기준이 된다(Project Management Institute, 2019, 2025).

실무에서 PM은 발주처와 합의한 수행계획서나 사업계획서를 바탕으로 WBS를 작성한다. 이 과정에서 PM은 문서에 흩어져 있는 기능 요구사항을 작업 단위로 나누고, 각 작업을 담당할 부서와 인력을 정하며, 작업 간 선후행 관계와 난이도를 고려하여 기간을 산정해야 한다. 이는 문서의 내용을 정확히 이해하는 동시에 유사 프로젝트의 경험을 바탕으로 판단해야 하는 작업으로, 같은 문서라도 작성자의 경험에 따라 결과가 달라질 수 있다.

계획을 세운 뒤에는 회의를 통해 프로젝트를 운영한다. 프로젝트 착수 시점의 킥오프 회의, 주기적인 진도 점검 회의, 문제가 생겼을 때의 이슈 체크 회의, 주요 분기에서의 합의 회의 등 목적이 다른 회의가 프로젝트 기간 내내 이어진다. 회의 연구에서는 안건을 미리 정하여 사용하는 것이 참석자가 인식하는 회의 효과성과 관련이 있음을 보고하였다(Leach et al., 2009). 또한 회의에서 정한 후속 조치가 기록되지 않거나 다음 회의로 이어지지 않으면, 결정 사항이 실제로 실행되었는지 추적하기 어렵다. 특히 WBS와 회의 기록이 서로 다른 도구에 흩어져 있으면, PM은 계획 대비 진행 상황과 미결 사항을 한곳에서 파악하기 어렵다.

현재 널리 쓰이는 프로젝트 관리 도구와 협업 도구는 작업 목록, 일정표, 회의록을 기록하고 공유하는 기능을 제공하며, 최근에는 생성형 인공지능을 이용해 작업을 나누거나 회의 내용을 요약하는 기능도 도입하고 있다(Atlassian, n.d.-b; Microsoft, n.d.; NAVER WORKS, n.d.-a; Notion Labs, n.d.). 그러나 이러한 기능은 계획 수립과 회의 기록 가운데 한쪽에만 적용되어, 계획에서 회의로, 회의에서 후속 조치로 이어지는 흐름은 여전히 PM이 직접 연결해야 한다.

한편 최근의 대규모 언어 모델(Large Language Model, LLM)은 긴 문서를 읽고 요약하거나, 문서에서 필요한 정보를 추출하여 정해진 형식의 구조화된 데이터로 출력하는 과업에 활발히 활용되고 있으며, 프로젝트 설명으로부터 작업 흐름을 생성하는 연구도 보고되었다(Hou et al., 2024; Sarim et al., 2025). 이는 PM이 수행계획서를 읽고 WBS 초안을 만드는 과정의 상당 부분을 자동화할 수 있는 가능성을 보여 준다. 다만 LLM의 출력은 사실과 다르거나 형식이 어긋날 수 있으므로, 생성 결과를 그대로 쓰기보다는 PM이 근거를 확인하고 수정한 뒤 확정하는 과정이 필요하다. 또한 외부 LLM이 제공하는 응용 프로그래밍 인터페이스(Application Programming Interface, API)는 호출량 제한이나 일시적인 장애로 요청이 실패할 수 있으므로, 이를 실제 서비스에 적용하려면 호출 실패에 대비한 설계가 함께 이루어져야 한다.

이러한 배경에서 본 연구는 수행계획서로부터 WBS 초안을 자동으로 생성하고, 이를 바탕으로 회의 운영과 후속 조치 관리까지 하나의 흐름으로 지원하는 PM 지원 시스템이 필요하다고 보았다.

## 나. 연구 목적

본 연구의 목적은 LLM을 활용하여 PM의 계획 수립과 회의 운영을 지원하는 플랫폼인 컨펌(Confirm)[^1]을 설계하고 구현하며, 그 유효성을 평가하는 것이다. 구체적인 목표는 다음과 같다.

첫째, WBS 자동 생성 기능을 구현한다. PM이 수행계획서를 업로드하면 시스템이 문서의 텍스트를 추출하고, LLM을 이용하여 담당 부서, 기간, 선후행 관계를 갖춘 WBS 초안을 생성한다. 이때 각 작업의 기간과 배정에 대한 산정 근거를 함께 생성하여, PM이 자동 생성 결과를 검토하고 수정한 뒤 확정할 수 있도록 한다.

둘째, 회의 운영 지원 기능을 구현한다. 회의 유형별 표준 체크리스트를 제공하여 회의 준비를 돕고, 회의가 끝나면 체크리스트 달성률을 계산하며, 처리하지 못한 안건을 Action Item으로 전환하여 다음 회의에 이월한다. 또한 확정된 WBS의 일정을 바탕으로 필요한 회의와 그 시점을 추천한다.

셋째, 일정 통합 관리 기능을 구현한다. WBS와 회의 일정을 표, 간트 차트, 캘린더로 함께 보여 주어, 계획과 회의를 서비스 안의 한곳에서 파악할 수 있도록 한다.

넷째, 구현한 시스템을 평가한다. 생성된 WBS의 형식과 구조를 자동 지표로 측정하고 전문가 평가로 실무적 품질을 확인하며, 여러 LLM의 생성 결과와 응답 시간, 비용을 비교한다. 또한 LLM 호출 실패에 대비한 재시도와 대체 모델 처리의 효과를 확인하고, 실제 사용자를 대상으로 사용성을 평가한다.

## 다. 연구 범위 및 방법

본 연구의 범위는 다음과 같다. 입력 문서는 텍스트 계층이 있는 PDF 형식의 수행계획서로 한정한다. 광학 문자 인식(Optical Character Recognition, OCR)이 필요한 스캔 문서와 HWP 형식의 문서는 다루지 않는다. 시스템의 기본 LLM으로는 Gemini 2.5 Flash를 사용하며, 다른 LLM은 성능 비교 실험에서만 사용한다. 사용자는 하나의 프로젝트에 참여하는 PM과 팀원으로 가정하고, 프로젝트 생성과 팀원 관리, WBS 생성과 확정, 회의와 Action Item 관리, 일정 시각화를 구현 범위에 포함한다. 서비스 기획 단계에서 함께 정의하였던 기능 가운데, 회의 음성을 텍스트로 변환(Speech-to-Text, STT)하여 체크리스트 이행 여부를 실시간으로 검증하는 기능과 네이버웍스(Naver Works), 노션(Notion) 등 외부 협업 도구로 알림을 보내는 기능은 본 연구의 범위에서 제외하고 향후 연구 과제로 남긴다.

연구는 다음의 순서로 진행한다. 먼저 PM의 업무 흐름을 계획 수립, 회의 운영, 일정 관리의 세 영역으로 나누어 기능 요구사항과 비기능 요구사항을 도출한다. 다음으로 이를 바탕으로 시스템 아키텍처, 데이터베이스, API, 인증과 접근 제어를 설계한다. 이어서 NestJS 기반의 서버와 React 기반의 클라이언트, PostgreSQL 데이터베이스로 시스템을 구현하고, WBS 생성과 회의 추천을 위한 프롬프트를 설계하며, LLM 호출의 안정성을 높이기 위한 재시도와 대체 모델 처리를 적용한다. 마지막으로 실제 수행계획서를 이용한 WBS 생성 실험과 전문가 평가, LLM 모델 간 비교 실험, 오류 주입을 통한 호출 안정성 검증, 사용자를 대상으로 한 사용성 평가를 수행하여 시스템을 평가한다.

## 라. 논문 구성

본 논문은 다음과 같이 구성된다. 2장에서는 프로젝트 관리와 WBS, 회의 관리와 의사결정 추적, LLM 기반 문서 분석에 관한 관련 연구를 살펴보고, 기존 프로젝트 관리 도구와 비교하여 본 연구의 차별점을 정리한다. 3장에서는 요구사항 분석을 바탕으로 시스템 아키텍처, 데이터베이스, API, 인증과 보안을 설계한다. 4장에서는 WBS 자동 생성, WBS 기반 회의 추천, 회의 어시스트, 일정 시각화, 사용자 인터페이스의 구현 내용을 기술한다. 5장에서는 실험을 통해 생성된 WBS의 품질과 LLM 모델별 성능, 호출 안정성, 시스템의 사용성을 평가하고 그 결과를 논의한다. 마지막으로 6장에서는 연구 내용을 요약하고 연구의 의의와 한계, 향후 연구 방향을 제시한다.

[^1]: 서비스 화면과 LLM 프롬프트에서는 서비스 이름을 "Conf:rm"으로 표기한다. 본 논문에서는 읽기 쉽도록 "Confirm"으로 쓴다.
