# 2. 관련 연구

본 장에서는 컨펌의 설계와 구현의 바탕이 되는 이론과 기존 연구를 살펴본다. 먼저 프로젝트 관리에서 WBS와 일정 수립의 개념을 정리하고, 이어서 회의 운영과 후속 조치 관리에 관한 연구를 살펴본다. 다음으로 LLM의 발전 과정과 이를 활용하기 위한 프롬프트 설계 및 구조화된 출력 기법을 정리한다. 마지막으로 기존 프로젝트 관리 도구를 분석하고, 기존 연구와 도구의 한계에 비추어 본 연구의 차별점을 제시한다.

## 가. 프로젝트 관리와 WBS

### 1) WBS의 개념과 작성 원칙

WBS는 프로젝트 목표를 달성하고 필요한 산출물을 만들기 위해 수행해야 할 전체 작업 범위를 계층적으로 분해한 구조이다(Project Management Institute, 2019, 2025). 최상위에는 프로젝트 전체가 놓이고, 아래로 내려갈수록 산출물이나 작업이 더 작은 단위로 나뉜다. 가장 하위 수준의 단위를 작업 패키지(work package)라 하며, 작업 패키지는 비용과 기간을 산정하고 담당자를 배정하며 진척을 관리하는 기본 단위가 된다.

WBS를 작성할 때 널리 쓰이는 원칙은 다음과 같다. 첫째, 하위 요소를 모두 합치면 상위 요소의 범위와 정확히 같아야 하며, 프로젝트 범위에 포함되지 않는 작업은 넣지 않는다. 이를 100% 규칙이라 한다. 둘째, 같은 수준의 요소끼리는 범위가 겹치지 않아야 한다. 셋째, 작업 패키지는 한 명의 책임자나 한 조직이 맡을 수 있고, 기간과 비용을 신뢰성 있게 추정할 수 있을 만큼 작아야 한다. 다만 지나치게 잘게 나누면 관리 부담이 커지므로, 실무에서는 작업 패키지의 크기에 대한 경험적 기준을 함께 활용한다(Project Management Institute, 2019).

WBS 작성 방법으로는 프로젝트 전체에서 출발하여 단계적으로 나누어 내려가는 하향식 분해, 과거 유사 프로젝트의 WBS를 템플릿으로 재사용하는 방법, 전문가의 판단에 의존하는 방법 등이 있다. 어떤 방법을 쓰더라도 요구사항 문서를 해석하고 적절한 분해 수준을 정하는 일은 작성자의 경험에 크게 의존한다. 이 때문에 경험이 적은 PM이 작성하거나 새로운 도메인의 프로젝트를 다룰 때에는 작업 누락이나 분해 수준의 불균형 같은 문제가 생길 수 있다.

컨펌의 WBS 생성 프롬프트는 이러한 작성 원칙을 반영한다. 기능 명세를 특정 부서 하나가 전담할 수 있는 최소 작업 단위로 나누도록 한 것은 작업 패키지의 책임 단일성 원칙에 대응한다.

### 2) 작업 간 의존성과 일정 수립

WBS로 작업을 정의한 다음에는 작업 사이의 순서와 기간을 정하여 일정을 수립한다. 작업 간 의존 관계는 선행 작업과 후행 작업의 시작과 종료 시점을 어떻게 연결하는지에 따라 종료-시작(Finish-to-Start), 시작-시작(Start-to-Start), 종료-종료(Finish-to-Finish), 시작-종료(Start-to-Finish)의 네 가지로 구분된다. 이 가운데 선행 작업이 끝나야 후행 작업을 시작할 수 있는 종료-시작 관계가 가장 많이 쓰인다. 작업과 의존 관계를 노드와 화살표로 나타낸 네트워크 도표를 선후행 도표법(Precedence Diagramming Method, PDM)이라 한다(Project Management Institute, 2017).

작업 기간은 과거 유사 작업의 실적을 근거로 하는 유추 추정, 작업량과 생산성 같은 변수로 계산하는 모수 추정, 낙관·최빈·비관 값을 함께 고려하는 3점 추정 등으로 산정한다. 의존 관계와 기간이 정해지면 주공정법(Critical Path Method, CPM)으로 프로젝트 전체 기간을 결정하는 가장 긴 경로, 즉 주공정을 찾을 수 있다(Kelley & Walker, 1959; Malcolm et al., 1959). 일정을 단축해야 할 때는 서로 의존하지 않는 작업을 병렬로 진행하거나(fast tracking), 자원을 추가 투입하는 방법을 쓴다. 이렇게 수립한 일정은 작업을 가로 막대로 나타내는 간트 차트로 시각화하는 경우가 많다.

컨펌은 LLM이 각 태스크의 선행 태스크 목록을 출력하도록 하여 종료-시작 관계를 표현하고, 작업의 난이도와 담당자의 경력에 따라 기간을 차등 배정하며, 의존 관계가 없는 작업은 병렬로 배치하도록 지시한다. 생성된 일정은 간트 차트와 캘린더로 시각화한다. 반면 종료-시작 이외의 의존 관계 유형, 주공정 계산, 자원 평준화는 현재 구현 범위에 포함하지 않는다.

## 나. 회의 관리와 의사결정 추적

### 1) 회의 유형별 운영 방식

프로젝트 회의는 목적에 따라 여러 유형으로 나눌 수 있으며, 본 연구에서는 다음 네 가지로 구분한다. 킥오프 회의는 프로젝트 착수 시점에 이해관계자와 팀원이 모여 목표와 범위, 역할과 책임, 일정, 의사소통 방식을 공유하는 회의이고, 진도 점검 회의는 정해진 주기마다 계획 대비 진척을 확인하고 지연 요소를 파악하는 회의이다(Project Management Institute, 2017). 이슈 체크 회의는 문제가 발생했을 때 원인을 분석하고 해결 방안과 담당자를 정한다. 합의 회의는 설계 확정이나 산출물 승인처럼 다음 단계로 넘어가기 위한 의사결정을 내린다.

회의 효과성에 관한 연구에서는 안건의 사용이 참석자가 인식하는 회의 효과성을 예측하는 중요한 설계 요소임을 보고하였다(Leach et al., 2009; Rogelberg, 2019). 안건이 미리 정해져 있으면 참석자가 준비할 수 있고, 논의가 목적에서 벗어나는 것을 줄일 수 있다. 또한 반복적으로 수행하는 업무에서 필수 항목을 체크리스트로 정리하면 중요한 항목의 누락을 줄일 수 있다. 의료 분야에서는 수술 안전 체크리스트를 도입한 뒤 합병증과 사망률이 줄었다는 결과가 보고되었다(Haynes et al., 2009).

컨펌은 이러한 회의 유형을 킥오프, 진도 점검, 이슈 체크, 합의의 네 가지로 정의하고, 유형마다 반드시 다루어야 할 안건을 표준 체크리스트로 제공한다.

### 2) Action Item 관리와 미결 사항 이월

회의의 결과물은 크게 의사결정과 후속 조치로 나뉜다. 후속 조치는 회의에서 합의한 할 일로, 담당자와 마감일이 정해져야 실행으로 이어진다. 이를 흔히 Action Item이라 부르며, 프로젝트 관리 문헌은 미결 사항과 후속 조치를 이슈 기록부(issue log)나 조치 목록으로 관리하도록 권장한다(Project Management Institute, 2017). 소프트웨어 개발 분야에서는 주요 설계 결정과 그 근거를 기록하는 의사결정 기록(Architecture Decision Record, ADR)과 같은 방법도 쓰인다(Nygard, 2011).

그러나 회의록과 조치 목록을 사람이 따로 정리해야 하는 경우 기록이 누락되거나, 다음 회의에서 이전 조치의 진행 상황을 확인하지 못할 수 있다. 최근에는 LLM으로 회의 내용을 요약하고 Action Item을 추출하는 시스템도 연구되고 있으나, 사용자 평가에서 중요한 내용이 누락되거나 참석자별로 관련 있는 내용을 가려내지 못하는 한계가 보고되었다(Asthana et al., 2025).

컨펌은 회의를 완료할 때 체크리스트에서 이행되지 않은 항목을 자동으로 Action Item으로 전환하고, 완료되지 않은 Action Item을 이월 항목으로 표시하여 다음 회의 화면에 보여 준다. 이를 통해 기록과 이월을 사람의 기억이나 별도 정리에 의존하지 않도록 하였다.

## 다. 대규모 언어 모델(LLM) 기반 문서 분석

### 1) 대규모 언어 모델 개요

LLM은 대규모 텍스트 데이터로 사전 학습된 신경망 언어 모델로, 대부분 트랜스포머(Transformer) 구조를 바탕으로 한다(Vaswani et al., 2017). 모델과 학습 데이터의 규모가 커지면서 LLM은 별도의 추가 학습 없이 프롬프트에 주어진 지시와 몇 개의 예시만으로 다양한 과제를 수행하는 능력을 보였다(Brown et al., 2020). 이후 사람의 지시를 따르도록 추가로 학습하는 지시 학습과 사람의 피드백을 활용한 강화 학습이 적용되면서, 사용자의 자연어 지시를 이해하고 원하는 형식으로 답하는 능력이 크게 향상되었다(Ouyang et al., 2022).

최근의 상용 LLM은 최대 100만 토큰 규모의 입력을 한 번에 처리할 수 있어, 수십 쪽 분량의 문서를 나누지 않고 그대로 분석할 수 있다(Anthropic, n.d.-a). 또한 답을 내기 전에 내부적으로 추론 과정을 거치는 기능을 갖춘 모델도 제공되고 있다(Anthropic, n.d.-b). 이러한 모델은 클라우드 API 형태로 제공되므로, 응용 시스템은 모델을 직접 운영하지 않고 API를 호출하여 기능을 구현할 수 있다.

그러나 LLM에는 응용 시스템이 고려해야 할 한계도 있다. 첫째, 입력 문서에 없는 내용을 사실처럼 생성하는 환각(hallucination)이 발생할 수 있다(Ji et al., 2023). 둘째, 같은 입력에도 출력이 달라질 수 있어 결과의 재현성이 낮다. 셋째, 외부 API는 호출량 제한과 일시적인 장애, 응답 지연, 사용량에 따른 비용이 따르며, 모델에 따라 품질, 속도, 비용 사이의 상충 관계가 있다. 이러한 한계 때문에 LLM의 출력을 업무에 활용하려면 사람이 결과를 검토할 수 있는 장치와 호출 실패에 대비한 설계가 필요하다.

LLM을 프로젝트 관리나 소프트웨어 개발에 적용하려는 연구도 활발하다. Hou et al.(2024)에서는 2017년 1월부터 2024년 1월까지 발표된 395편의 논문을 분석하여 LLM이 소프트웨어 공학의 여러 과업에 적용되는 양상을 정리하였다. 요구사항 공학 분야에서는 2023년과 2024년에 발표된 74편의 연구를 분석한 결과, 요구사항 도출과 검증에 연구가 집중되어 있고 제로샷·퓨샷 프롬프트를 주로 사용하며, 대부분 통제된 환경에서 평가되어 산업 현장에 적용된 사례는 적은 것으로 나타났다(Zadenoori et al., 2025).

본 연구와 가장 가까운 연구인 Sarim et al.(2025)에서는 소프트웨어 프로젝트 설명으로부터 작업 흐름을 생성하는 과제를 대상으로 다섯 가지 LLM과 다섯 가지 프롬프트 전략(제로샷, 퓨샷, 사고의 사슬, 역할 지정, ISO 21502 기반)을 비교하였다. 이들은 공개된 소프트웨어 제작 튜토리얼을 평가 자료로 사용하고, 문장 임베딩과 핵심 용어 일치도를 결합한 유사도 지표를 제안하여 생성된 작업 흐름을 평가하였다. 건설 분야에서는 여러 인공지능 에이전트가 역할을 나누어 WBS와 주공정 일정을 작성하게 하여, 숙련자가 약 480분 걸리던 작성 시간을 약 20분으로 줄였다는 결과가 보고되었다(Korba & Pawluk, 2026). 회의 분야에서는 LLM으로 회의 요약과 Action Item을 생성하는 시스템을 실제 업무 회의에서 평가한 연구가 있다(Asthana et al., 2025).

이러한 연구들은 LLM이 작업 분해와 일정 수립을 돕는 데 활용될 수 있음을 보여 준다. 그러나 대부분 작업 흐름 생성이나 회의 요약처럼 하나의 과업을 따로 다루며, 실제 수행계획서에서 팀 구성을 반영하여 부서·기간·선후행 관계를 갖춘 WBS를 만들고 이를 회의 운영까지 이어 가는 과정을 다룬 연구는 찾기 어렵다.

### 2) 프롬프트 엔지니어링과 구조화된 출력

프롬프트 엔지니어링은 LLM이 원하는 결과를 내도록 입력 지시문을 설계하는 기법이다. 대표적인 기법으로는 예시 없이 지시만 주는 제로샷 프롬프트, 몇 개의 입출력 예시를 함께 주는 퓨샷 프롬프트, 모델에게 특정 전문가의 역할을 부여하는 역할 지정 등이 있다. 복잡한 문제에서는 최종 답을 바로 요구하기보다 중간 추론 과정을 단계적으로 거치도록 유도하면 성능이 높아진다는 연구가 있으며, 이를 사고의 사슬(chain-of-thought) 프롬프트라 한다(Kojima et al., 2022; Wei et al., 2022). 또한 지시문과 입력 데이터를 구분 기호나 태그로 명확히 나누면 모델이 둘을 혼동하는 것을 줄일 수 있어, LLM 공급자의 프롬프트 작성 지침에서도 이를 권장한다(Anthropic, n.d.-c).

LLM의 출력을 응용 시스템에서 처리하려면 출력이 정해진 구조를 따라야 한다. 이를 위해 프롬프트에 출력 형식의 스키마와 예시를 제시하고 형식 외의 텍스트를 금지하는 방법, 응답을 받은 뒤 스키마에 맞는지 검증하고 실패하면 다시 요청하는 방법, 그리고 모델이 생성 단계에서 지정한 JSON(JavaScript Object Notation) 스키마를 지키도록 강제하는 구조화된 출력 기능을 사용하는 방법이 있다(Willard & Louf, 2023).

컨펌의 WBS 생성 프롬프트는 역할 지정, 정보 추출부터 일정 산정까지의 단계적 지시, JSON 스키마 제시, 출력 제약을 함께 사용한다. 또한 태스크마다 기간과 배정의 근거를 함께 출력하게 하여, 단계적 추론의 결과를 사용자가 검토할 수 있는 형태로 남긴다. 서버는 응답을 JSON으로 해석하고 필수 구조를 검증한 뒤 저장한다.

## 라. 기존 프로젝트 관리 도구 분석

현재 프로젝트 관리와 협업에 널리 쓰이는 도구들을 WBS·일정 관리, 회의 관리, 인공지능 기능의 측면에서 비교하면 [표 1]과 같다. 도구의 기능은 계속 바뀌므로, 비교 내용은 2026년 11월 18일에 확인한 각 도구의 공식 문서를 기준으로 한다.

## 마. 기존 연구 및 도구의 한계와 본 연구의 차별점

앞에서 살펴본 내용을 정리하면, 기존 도구와 연구에는 다음과 같은 한계가 있다. 첫째, 기존 프로젝트 관리 도구에도 작업 분해나 계획 생성, 회의 요약을 돕는 인공지능 기능이 도입되고 있으나, 이는 개별 과업을 돕는 데 초점이 있으며 자동 생성한 계획을 검토하는 데 필요한 산정 근거를 함께 제공하는지는 공개된 문서에서 확인되지 않는다. 둘째, 계획 수립 도구와 회의·후속 조치 관리 도구가 분리되어 있어, 계획에서 회의로, 회의에서 후속 조치로 이어지는 흐름을 사람이 직접 연결해야 한다. 셋째, LLM을 프로젝트 관리에 적용한 연구는 작업 흐름 생성이나 회의 요약처럼 개별 과업에 초점을 맞추고 있으며, 생성 결과를 사람이 검토하여 확정하는 과정이나 외부 API 호출의 안정성처럼 실제 서비스에 적용할 때 필요한 요소를 다룬 경우는 적다.

본 연구는 이러한 한계에 대해 다음과 같은 차별점을 가진다.

첫째, 수행계획서를 입력으로 받아 담당 부서, 기간, 선후행 관계를 갖춘 WBS 초안을 자동으로 생성한다. 이때 태스크마다 산정 근거를 함께 생성하고, PM이 이를 검토하여 수정한 뒤 확정하는 과정을 두어, 자동 생성의 효율과 사람의 판단을 함께 반영한다.

둘째, WBS 생성, 회의 생성과 추천, 회의 체크리스트, Action Item 이월을 하나의 시스템에서 연결한다. WBS가 생성되면 킥오프 회의가 자동으로 만들어지고, 회의에서 처리하지 못한 안건은 Action Item으로 전환되어 다음 회의로 이어진다.

셋째, LLM을 실제 서비스에 적용하는 데 필요한 안정성을 고려하였다. 외부 API의 일시적 오류에 대비하여 지수 백오프(exponential backoff) 재시도와 대체 모델 폴백(fallback)을 적용하고, 그 동작을 오류 주입 실험으로 검증한다. 지수 백오프는 실패한 요청을 대기 시간을 두 배씩 늘려 가며 다시 보내는 방식이고, 폴백은 기본 모델을 사용할 수 없을 때 미리 정한 다른 모델로 넘어가는 방식이다.

넷째, 생성된 WBS를 형식과 구조의 자동 지표, 전문가 평가, 여러 LLM 간의 비교로 정량적으로 평가하는 방법을 제시한다.

다만 본 연구는 종료-시작 이외의 의존 관계, 주공정 계산, 자원 평준화와 같은 정밀한 일정 계산 기능을 다루지 않으며, 이는 기존의 일정 관리 도구가 강점을 갖는 부분이다. 본 연구는 정밀한 일정 최적화보다는 문서에서 계획 초안을 빠르게 얻고 이를 회의 운영과 연결하는 데 초점을 둔다.
