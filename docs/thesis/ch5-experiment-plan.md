## 0. 요약

## 1. 현재 상태 점검

실험 설계 전에 저장소에서 확인한 사실이다.

- **평가 데이터가 사실상 1건뿐이다.** git 이력에 업로드 PDF 9개가 있었지만 모두 같은 파일(468,333바이트)을 반복 업로드한 것이다. 수행계획서를 5~10건 새로 확보해야 한다.
- **LLM은 Gemini만 동작한다.** Claude 호출 코드는 주석 처리되어 있고, 예전 모델(`claude-sonnet-4-6`)과 `max_tokens: 4000`으로 작성되어 있다. 4,000 토큰이면 태스크가 많은 WBS는 JSON이 중간에 잘릴 수 있으므로, 살릴 때는 값을 늘려야 한다. OpenAI SDK는 설치되어 있지 않다.
- **생성 설정을 지정하지 않는다.** Gemini 호출에 temperature 등 생성 설정이 없어 기본값으로 동작한다. 재현성을 위해 실험 시 설정값을 기록해야 한다.
- **측정 기능이 없다.** 응답 시간, 재시도 횟수, 사용한 폴백 모델, 토큰 수를 저장하지 않는다(재시도·폴백은 로그 메시지로만 남는다). 앱 코드와 별도로 평가 스크립트가 필요하다.
- **회의 추천은 화면에 연결되지 않았다.** API로만 평가할 수 있으므로 사용성 평가 과업에서는 빼야 한다.
- **구글 캘린더 동기화는 현재 버전에서 동작하지 않는다.** 6월 2일 커밋(f11e476)에서 로그인 권한 범위의 calendar.events를 제거하여 구글 갱신 토큰이 발급되지 않는다. 논문에서 이 기능을 다루지 않기로 하였으므로(2026-11-19) 평가 대상에서도 뺀다.

## 3. E1. WBS 생성 자동 평가

**목적:** 현재 시스템(Gemini 2.5 Flash + 현행 프롬프트)이 만든 WBS가 형식과 구조 면에서 얼마나 믿을 만한지 잰다.

**절차**

1. 각 문서의 PDF 텍스트를 현재 코드와 같은 방법(pdf-parse)으로 추출한다.
2. 문서마다 같은 조건으로 **3회** 생성한다. 반복은 결과의 흔들림을 보기 위함이다.
3. 호출마다 원본 응답, 응답 시간, 시도 횟수, 실제 사용 모델, 토큰 수(제공되는 경우)를 저장한다.
4. 아래 지표를 스크립트로 계산한다. 커버리지만 사람이 표시한다.

**지표**

| 지표 | 정의 | 계산 |
|---|---|---|
| JSON 파싱 성공률 | 응답을 JSON으로 해석할 수 있는 비율 | 자동 |
| 스키마 준수율 | 필수 필드가 모두 있고 타입이 맞는 비율 | 자동 |
| 절대 날짜 비율 | 시작일·종료일이 YYYY-MM-DD인 태스크 비율 (나머지는 D+N 또는 무효) | 자동 |
| 선행 참조 오류율 | 존재하지 않는 태스크 ID를 선행으로 가리키는 비율 | 자동 |
| 순환 의존 발생 | 선후행 관계에 순환이 있는 WBS 수 | 자동 |
| 일정 순서 위반율 | 선행 태스크 종료일 > 후행 태스크 시작일인 관계의 비율 | 자동 |
| 기간 불일치율 | duration_days와 (종료일 − 시작일 + 1)이 다른 태스크 비율 (영업일 계산 가능성 때문에 참고 지표) | 자동 |
| 부서 수, 태스크 수 | WBS 규모 | 자동 |
| 반복 일관성 | 같은 문서 3회 생성의 태스크 수·전체 기간 변동계수(CV) | 자동 |
| 기능 커버리지 | 정답 기능 중 1개 이상의 태스크가 다루는 비율 | 사람 |
| 응답 시간 | 평균, 중앙값, 90백분위 | 자동 |

## 5. E3. LLM 모델별 비교

**목적:** 같은 프롬프트와 입력으로 여러 LLM의 WBS 생성 결과, 응답 시간, 비용을 비교한다.

### 5.1 비교 모델 (제안)

| 구분 | 모델 | 모델 ID | 비고 |
|---|---|---|---|
| 기준 | Gemini 2.5 Flash | `gemini-2.5-flash` | 현재 시스템 기본 모델 |
| Claude 상위 | Claude Opus 5.5 | `claude-opus-5-5` | 현행 Claude 주력 모델 |
| Claude 경량 | Claude Haiku 5.5 | `claude-haiku-5-5` | Gemini Flash와 비슷한 저가·고속 등급 비교용 |
| GPT | [TODO: 실험 시점 모델명] | [TODO] | OpenAI SDK 설치 필요. 기획 문서에는 GPT-4o로 적혀 있음 |

- 주석 처리된 코드의 `claude-sonnet-4-6`은 이전 세대 모델이다. 실험에는 현행 모델을 쓰고, 논문에 **정확한 모델 ID와 실험 날짜**를 적는다.
- 모델이 많을수록 E2 평가 부담이 커진다. 최소 구성은 Gemini 2.5 Flash와 Claude 1종이다.

### 5.2 통제 조건

- 같은 시스템 프롬프트(`backend/src/prompts/wbs-generator.prompt.ts`), 같은 입력 텍스트, 같은 JSON 파싱·검증 코드를 쓴다.
- 문서마다 모델별로 3회씩 생성한다.
- **재시도와 폴백은 끄거나 모든 모델에 똑같이 적용**한다. 특히 Gemini의 폴백이 켜져 있으면 다른 모델의 결과가 섞이므로, 실제 사용한 모델을 반드시 기록한다.
- 출력 길이 상한은 모든 모델에 충분히 크게 준다(예: 16,000 토큰). 잘린 JSON은 별도로 집계한다.
- 생성 설정을 기록한다.
  - Gemini: 현재 기본값(temperature 미지정).
  - Claude 현행 모델은 temperature를 지정할 수 없고 thinking이 항상 켜져 있다. 대신 effort를 명시적으로 정해 기록한다(예: `medium`, Opus 5.5의 기본값). thinking 토큰도 출력 토큰으로 과금되므로 비용에 포함된다.

### 5.3 지표

E1의 자동 지표 전부, E2의 전문가 점수(블라인드), 그리고 다음을 더한다.

| 지표 | 정의 |
|---|---|
| 응답 시간 | 요청부터 응답 완료까지(평균, 중앙값, 90백분위) |
| 토큰 수 | 입력·출력 토큰 |
| 문서당 비용 | 입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가 |
| 잘림 발생 | 출력 상한에 걸려 JSON이 잘린 횟수 |

비용 계산에 쓰는 단가는 실험 날짜 기준으로 기록한다. 2026년 11월 기준 Claude 단가는 100만 토큰당 Opus 5.5가 입력 $4, 출력 $20이고, Haiku 5.5가 입력 $0.10, 출력 $0.50이다(입력 10만 토큰 이하 기준). Gemini와 GPT 단가는 [TODO: 실험 시점 공식 단가].

### 5.4 구현 방법 (권장)

앱의 `LlmService`를 고치지 않고, **별도 평가 스크립트**에서 같은 프롬프트로 각 공급자 API를 직접 호출한다. 앱 동작에 영향을 주지 않고 측정 항목(시간, 토큰, 시도 횟수)을 자유롭게 기록할 수 있다. 이 스크립트는 `backend/scripts/eval/`에 작성되어 있으며, 사용법은 [평가 스크립트 README](../../backend/scripts/eval/README.md)에 있다.

### 5.5 선택 실험: PDF 직접 입력

Claude는 PDF를 텍스트 추출 없이 그대로 입력받을 수 있다. 같은 문서를 "pdf-parse 추출 텍스트"와 "PDF 직접 입력"으로 각각 넣어 비교하면, 표·도식이 많은 문서나 스캔 문서에서 현재 텍스트 추출 방식의 한계를 보여 줄 수 있다. 4장에서 한계로 적은 OCR 미지원 문제와 연결된다.

## 6. E4. LLM 호출 안정화 효과

**목적:** 4장에서 구현한 지수 백오프 재시도와 모델 폴백이 실제로 실패를 줄였는지 보인다.

**절차**

1. E1(그리고 E3의 Gemini 실행)에서 호출마다 시도 횟수, 오류 코드, 최종 사용 모델을 기록한다.
2. 실험 중 자연적으로 발생한 오류가 적을 수 있으므로, **오류 주입 테스트**를 추가한다. 가짜 LLM 클라이언트가 503을 정해진 횟수만큼 반환하게 하여 재시도·폴백이 설계대로 동작하는지 확인한다. 이는 성능 측정이 아니라 동작 검증이다.

**지표:** 첫 시도 성공률, 최종 성공률, 재시도로 회복된 호출 비율, 폴백 발생 비율, 재시도로 늘어난 평균 지연 시간

**결과 표 양식**

[표 D] LLM 호출 안정성

## 7. E5. 사용성 평가

**목적:** 실제 사용자가 컨펌으로 계획 수립과 회의 운영을 수행할 수 있는지, 얼마나 쓰기 쉽고 유용하다고 느끼는지 평가한다.

### 7.1 참여자

- 5~8명. 프로젝트 관리 경험이 있는 사람(현업 PM, 팀 프로젝트 리더 경험 학생 등). [인용 필요: 소수 참여자 사용성 테스트의 근거]
- **사람을 대상으로 하는 연구이므로 대학원의 기관생명윤리위원회(IRB) 심의 대상인지 먼저 확인한다.** [TODO: IRB 확인]
- 참여자는 각자 구글 계정으로 로그인해야 한다. 테스트용 계정을 준비하는 것도 방법이다.

### 7.2 과업

미리 준비한 수행계획서 1건과 빈 프로젝트를 사용한다. 회의 추천은 과업에서 뺀다.

| 과업 | 내용 | 성공 기준 |
|---|---|---|
| T1 | 프로젝트를 만들고 팀원 1명을 이메일로 등록한다 | 팀원 목록에 등록됨 |
| T2 | 수행계획서를 업로드하고 WBS가 생성될 때까지 기다린다 | WBS 표가 나타남 |
| T3 | 태스크 1개의 기간을 고치고, 태스크 1개를 의사결정 지점으로 지정한 뒤 WBS를 확정한다 | 확정 상태, 수정 반영 |
| T4 | 진도 점검 회의를 만들고 체크리스트에 항목 1개를 추가한다 | 회의와 항목 생성됨 |
| T5 | 회의에서 체크리스트 일부를 완료로 표시하고 회의를 완료 처리한다 | 달성률 표시, Action Item 생성됨 |
| T6 | 새 회의를 만들고 이월된 Action Item을 확인한다 | 이월 항목을 찾아 말함 |

### 7.3 측정

- **과업 지표:** 과업 성공률, 수행 시간, 오류 또는 도움 요청 횟수
- **SUS(System Usability Scale):** 10문항 5점 척도, 0~100점으로 환산한다. [인용 필요: SUS 원문과 점수 해석 기준]
- **기능 유용성 설문(5점 척도):**
  - WBS 초안은 WBS를 처음부터 만드는 것보다 작업 시간을 줄여 준다.
  - 태스크별 산정 근거는 일정을 검토하는 데 도움이 된다.
  - 간트 차트와 캘린더로 일정을 한눈에 파악할 수 있다.
  - 회의 유형별 체크리스트는 회의 준비에 도움이 된다.
  - 이월된 Action Item 표시는 후속 조치를 관리하는 데 도움이 된다.
- **인터뷰:** 좋았던 점, 불편했던 점, 실무에서 쓰려면 필요한 기능

### 7.4 선택: 작업 시간 비교

참여자 일부가 같은 수행계획서로 (a) 스프레드시트에서 WBS 초안을 직접 만드는 시간과 (b) 컨펌으로 생성·검토·확정하는 시간을 잰다. 순서 효과를 줄이기 위해 절반은 (a)→(b), 절반은 (b)→(a) 순으로 한다. 효과를 가장 직접적으로 보여 주지만 참여자 부담이 크다.
