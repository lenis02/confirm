# 6. 결론

본 장에서는 컨펌의 설계, 구현, 평가 내용을 요약하고, 연구의 의의와 한계점, 향후 연구 방향을 제시한다.

## 가. 연구 요약

본 연구는 PM이 수행계획서를 바탕으로 WBS를 작성하고, 이를 회의 운영과 후속 조치 관리로 이어 가는 과정을 지원하기 위해, LLM을 활용한 PM 지원 플랫폼인 컨펌을 설계하고 구현하였다.

먼저 PM의 업무 흐름을 계획 수립, 회의 운영, 일정 관리의 세 영역으로 나누어 18개의 기능 요구사항과 7개의 비기능 요구사항을 도출하였다. 이를 바탕으로 React 기반의 클라이언트, NestJS 기반의 API 서버, PostgreSQL 데이터베이스로 이루어진 시스템을 설계하였으며, 10개 테이블로 구성된 데이터베이스와 45개의 엔드포인트로 구성된 API를 정의하였다. 보안 측면에서는 구글 OAuth 2.0과 JWT를 이용한 인증, 프로젝트 멤버십과 PM 역할에 기반한 접근 제어를 적용하였다.

핵심 기능으로는 첫째, 수행계획서 PDF에서 텍스트를 추출하고 LLM으로 WBS 초안을 생성하는 기능을 구현하였다. WBS 생성 프롬프트는 프로젝트 정보 추출, 태스크 분할, 의존성 기반 일정 산정의 세 단계로 지시를 구성하고, 태스크마다 담당 부서, 기간, 선행 태스크와 함께 기간과 배정의 산정 근거를 출력하도록 설계하였다. 생성된 WBS는 초안으로 저장되며, PM은 팀 구성과 태스크를 검토하고 의사결정 지점을 지정한 뒤 확정한다. 문서 분석은 백그라운드에서 비동기로 처리하고, LLM 호출에는 지수 백오프 재시도와 대체 모델 폴백을 적용하였다. 둘째, 확정된 WBS의 일정을 바탕으로 회의를 추천하는 API와 WBS 생성 직후 킥오프 회의를 자동으로 만드는 기능을 구현하였다. 셋째, 회의 유형별 표준 체크리스트, 회의 완료 시 체크리스트 달성률 계산, 이행하지 못한 안건의 Action Item 전환과 이월, 회의록 관리로 이루어진 회의 어시스트 기능을 구현하였다. 넷째, WBS를 표, 간트 차트, 부서별 보기로 보여 주고, WBS 일정과 회의를 합친 프로젝트 캘린더를 구현하였다.

구현한 시스템은 생성된 WBS의 자동 지표 평가, 전문가 평가, LLM 모델 간 비교, LLM 호출 안정성 검증, 사용성 평가의 다섯 가지 방법으로 평가한다. 오류 주입 실험에서는 일시적 과부하, 호출량 제한의 지속, 모델 없음, 요청 오류, 모든 모델의 과부하라는 다섯 가지 오류 상황에서 재시도와 대체 모델 처리가 설계한 시도 횟수와 대기 시간대로 동작함을 확인하였다. [TODO: 5장의 WBS 자동 평가, 전문가 평가, 모델 비교, 사용성 평가 결과를 수치와 함께 한 문단으로 요약]

## 나. 연구의 의의

본 연구의 의의는 다음과 같다.

첫째, 수행계획서에서 WBS를 만들고, 이를 회의 운영과 후속 조치 관리까지 이어 가는 과정을 하나의 시스템으로 구현하였다. 기존 도구들도 작업 분해나 회의 요약을 돕는 인공지능 기능을 도입하고 있으나 계획 수립과 회의 기록 가운데 한쪽에만 적용되는 데 비해, 컨펌에서는 WBS 생성이 킥오프 회의 생성으로, 회의에서 이행하지 못한 안건이 다음 회의의 이월 항목으로 자동으로 이어진다.

둘째, LLM이 만든 계획을 PM이 검토하고 확정하는 사람 참여형 구조를 제시하였다. 태스크마다 산정 근거를 함께 생성하여 PM이 자동 생성 결과의 이유를 확인할 수 있게 하고, 생성 결과를 초안으로 두어 PM의 수정과 확정을 거치도록 하였다. 이는 LLM의 출력이 사실과 다르거나 현실에 맞지 않을 수 있다는 한계를 고려하여, 자동화의 효율과 사람의 판단을 함께 반영하는 설계이다.

셋째, 외부 LLM API를 실제 서비스에 적용할 때 필요한 안정성 설계를 구현하고 검증하였다. LLM 호출을 공통 모듈로 추상화하여 공급자를 바꿀 수 있게 하고, 일시적 오류에 대한 재시도와 대체 모델 폴백을 적용하였으며, 그 동작을 오류 주입 실험으로 확인하였다.

넷째, LLM이 생성한 WBS를 평가하는 방법을 구체화하였다. JSON 파싱 성공률, 스키마 준수율, 선행 참조 오류율, 일정 순서 위반율, 기간 불일치율 같은 자동 지표와, 모델 이름을 숨긴 전문가 평가, 여러 LLM의 비교 실험을 평가 스크립트로 구현하여, 같은 조건에서 반복하여 측정할 수 있게 하였다.

## 다. 한계점 및 향후 연구

본 연구의 한계와 이를 보완하기 위한 향후 연구 방향은 다음과 같다.

첫째, 입력 문서의 형식이 제한적이다. 현재는 텍스트 계층이 있는 PDF만 처리하며, 스캔 문서와 HWP 형식의 문서는 다루지 못한다. 향후에는 OCR을 적용하거나, PDF를 텍스트 추출 없이 직접 입력받을 수 있는 LLM을 활용하여 표와 도식이 많은 문서까지 처리할 수 있도록 확장할 필요가 있다.

둘째, 생성된 WBS를 다루는 과정에 보완할 점이 있다. 문서에 구체적인 날짜가 없어 LLM이 상대 일자(D+N)를 출력한 태스크는 날짜가 비어 있는 상태로 저장되어 간트 차트와 캘린더에 표시되지 않는다. 또한 태스크를 삭제하면 표시 식별자를 다시 매기지만 다른 태스크의 선행 관계는 갱신하지 않으며, WBS를 확정하더라도 확정 시점의 일정을 별도로 보관하지 않고, 문서를 다시 업로드하면 확정된 WBS도 새 WBS로 대체된다. 향후에는 프로젝트 시작일을 기준으로 상대 일자를 실제 날짜로 변환하고, 선행 관계의 정합성을 유지하며, 확정된 WBS를 기준 일정으로 보존하는 버전 관리 기능을 도입할 필요가 있다.

셋째, 일정 계산 기능이 단순하다. 현재는 종료-시작 관계만 표현하며, 주공정 계산과 자원 평준화는 지원하지 않는다. LLM이 만든 초안 위에 주공정 계산을 더하면 PM이 일정 지연의 영향을 받는 태스크를 바로 파악할 수 있을 것이다.

넷째, 회의 추천 기능이 아직 완성되지 않았다. 회의 추천은 서버 API로만 구현되어 사용자 화면에 연결되지 않았으며, PM이 지정한 의사결정 지점 정보를 추천 입력에 포함하지 않는다. 의사결정 지점을 추천 입력에 반영하고 추천 결과를 화면에서 검토하여 등록하는 과정을 구현하는 것이 필요하다.

다섯째, 서비스 기획 단계에서 정의한 기능 가운데 일부를 구현하지 못하였다. 회의 음성을 텍스트로 변환하고 화자를 구분하여 체크리스트 이행 여부를 실시간으로 검증하는 기능과, 네이버웍스와 노션 등 외부 협업 도구로 일정과 할 일을 알리는 기능은 향후 연구 과제로 남긴다. 특히 실시간 검증 기능은 회의 중 PM의 기록 부담을 줄이고 체크리스트 달성률을 사람의 표시가 아닌 실제 논의 내용으로 산출할 수 있다는 점에서 의미가 있다.

여섯째, 운영 환경을 위한 보안과 데이터 관리를 보완해야 한다. 현재는 로그인 직후 토큰을 URL로 전달하고 브라우저 저장소에 보관하며, 로그아웃 시 서버에서 토큰을 무효화하지 않는다. 또한 데이터베이스 스키마를 엔티티 정의로부터 자동으로 동기화한다. 운영 환경에서는 갱신 토큰을 HttpOnly 쿠키로 전달하고 사용할 때마다 교체하며, 스키마 변경은 마이그레이션으로 관리하는 방식으로 전환할 필요가 있다.

일곱째, WBS 생성 프롬프트가 IT 프로젝트를 전제로 한다. 문서에 팀 정보가 없을 때 기획, 디자인, 프론트엔드, 백엔드 역할을 가정하도록 설계되어 있어, 다른 분야의 프로젝트 문서에서는 부서 구성이 맞지 않을 수 있다. 분야별 프롬프트나 조직의 기존 WBS를 예시로 활용하는 방법을 검토할 필요가 있다.

여덟째, 평가에도 한계가 있다. LLM은 같은 입력에도 출력이 달라질 수 있고 모델이 계속 갱신되므로, 본 연구의 실험 결과는 실험 시점의 모델과 설정에 따른 것이다. [TODO: 5장 실험 후 평가 문서의 수와 분야, 전문가와 사용성 평가 참여자의 수 등 평가 규모에 따른 한계를 추가]

향후에는 이러한 한계를 보완하는 한편, 실제 프로젝트 팀이 컨펌을 일정 기간 사용하는 현장 평가를 통해 WBS 자동 생성과 회의 지원이 프로젝트 관리의 효율과 품질에 미치는 영향을 장기적으로 검증할 필요가 있다.
